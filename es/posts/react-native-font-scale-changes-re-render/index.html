React Native en Android: los cambios de escala de fuente en vivo no re-renderizan lo que crees

julio 8, 2026 4 minutos de lectura.
Ingeniería
React-Native • Android • Accesibilidad • Debugging • Expo

El síntoma Link to heading

Un tester de QA subió el tamaño de fuente del sistema en Display size & text de Android mientras la app estaba abierta, volvió a la app, y encontró labels de botones y chips de estado truncados — "Deposit" se convertía en "Dep..", "Completed" en "Complet". Un fix previo para un defecto relacionado de “la app no carga” ya se había desplegado, así que parecía una regresión.

Primera teoría: es un bug de memo (parcialmente cierto) Link to heading

React Native expone un multiplicador de escala vía useWindowDimensions().fontScale. Nuestro componente de botón lo usaba para calcular un estilo de label escalado manualmente:

1
2
3
4

const combinedLabelStyle = useMemo(() => {
    return { ...getLabelStyle(theme, size, fontScale), ...labelStyle };
    // eslint-disable-next-line react-hooks/exhaustive-deps
}, [theme, size, labelStyle]); // <-- fontScale se usa dentro, pero falta en las deps

El eslint-disable escondía un bug real: cuando el tamaño de fuente del sistema cambiaba con la app en foreground, este memo nunca se recalculaba. El botón seguía usando su tamaño de fuente original mientras el Text subyacente (que auto-escala salvo allowFontScaling={false}) renderizaba más grande — desajuste, contenedor muy angosto, entra el ellipsis.

Arreglar el array de dependencias hizo que los botones escalaran correctamente. Pero un componente distinto (un chip de estado) mostraba el mismo síntoma, y ni siquiera referenciaba fontScale en sus estilos.

Segunda teoría: nada se re-renderiza (también cierto) Link to heading

Probando en vivo, en un emulador, con adb shell settings put system font_scale X mientras la app estaba en foreground: nada se actualizaba — ni el botón, ni el chip, ni siquiera un <Text> plano mostrando un monto en dólares. Hasta el título nativo del header se truncaba. Eso descartaba un bug de un solo componente; algo más fundamental no estaba propagando el cambio a JS en absoluto.

Al revisar el código fuente de Android de react-native (DeviceInfoModule.kt) apareció la explicación:

1
2
3
4
5
6
7

override fun onHostResume() {
    val newFontScale = reactApplicationContext.resources?.configuration?.fontScale
    if (newFontScale != null && newFontScale != fontScale) {
        fontScale = newFontScale
        emitUpdateDimensionsEvent()
    }
}

Dimensions/useWindowDimensions() en Android solo se actualiza en el callback de resume del lifecycle de la Activity — no en onConfigurationChanged. Si cambias el tamaño de fuente sin mandar la app a background, React Native no tiene forma de enterarse de nada hasta el próximo resume.

Esto importa porque un fix anterior había agregado deliberadamente fontScale|density a android:configChanges en MainActivity, específicamente para que un cambio de tamaño de fuente no destruyera y recreara la Activity (eso causaba un bug de “la splash nunca se oculta”). El efecto secundario: Android ya no destruye el árbol de vistas ante un cambio de tamaño de fuente, y la propia detección de cambio de dimensiones de RN solo corre en el resume — así que nada se refresca a menos que el usuario realmente mande la app a background y vuelva a foreground.

El fix real, en dos partes Link to heading

  1. Suscribirse. Cualquier componente cuyo layout dependa de fontScale debe llamar useWindowDimensions() él mismo, no confiar en que un padre se lo pase como prop y que ese prop se actualice. Sin la suscripción, el componente no tiene motivo para re-renderizar en el resume.

  2. Forzar la re-medición, no solo el re-render. Incluso suscribiéndose, un cambio de estilo nada más no bastaba — la medición nativa del TextView en Android queda cacheada y no vuelve a hacer layout solo porque cambió la referencia de un objeto StyleSheet. El fix confiable fue usar el valor de escala como key del componente:

    1

    <Pressable key={`fontscale-${fontScale.toFixed(2)}`} ...>

    Esto fuerza un unmount/remount completo, exactamente equivalente a un arranque en frío de la app con esa escala de fuente — que ya habíamos confirmado que renderiza correctamente.

Cómo probar esto de verdad Link to heading

La forma fácil de obtener un falso negativo: cambiar la escala de fuente vía ADB con la app en foreground. Eso se salta el único camino de código (onHostResume) que detecta el cambio.

1
2
3

adb shell input keyevent KEYCODE_HOME        # manda la app a background — obligatorio
adb shell settings put system font_scale 1.5 # cambia la escala estando en background
adb shell am start -n <package>/.MainActivity # vuelve a foreground (resume real)

Cualquier cosa que no sea un ciclo real de background → cambio → foreground no está probando el bug que realmente le pasa a los usuarios.

Conclusiones Link to heading

  • Los trade-offs de android:configChanges cortan para los dos lados: prevenir la recreación de la Activity arregla una clase de bug (splash congelada/en blanco) pero reintroduce silenciosamente estado obsoleto en todo lo que asumía un mount fresco ante cada cambio de configuración relevante.
  • Un eslint-disable-next-line react-hooks/exhaustive-deps vale la pena tratarlo como pregunta abierta, no como respuesta zanjada — acá escondía una dependencia que sí importaba.
  • “Se re-renderiza” y “vuelve a hacer layout correctamente” son garantías distintas en plataformas nativas. Un remount vía key es una válvula de escape legítima, a veces necesaria, cuando actualizar el estilo no alcanza para forzar que las vistas nativas se vuelvan a medir.
