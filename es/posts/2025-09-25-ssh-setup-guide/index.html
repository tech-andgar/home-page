Resumen Ejecutivo Link to heading

Este documento establece una metodología completa para gestionar múltiples claves SSH en la estación de trabajo de un desarrollador. El objetivo principal es asegurar una segregación clara y segura de las identidades digitales (por ejemplo, personal vs. trabajo) para interactuar con repositorios Git (GitHub, GitLab, etc.) y acceder a servidores remotos. Al adoptar esta guía, mejorarás la seguridad aplicando el principio de privilegio mínimo, reducirás el riesgo de errores de atribución en los commits y crearás una solución escalable para gestionar el acceso a diversos recursos. Esta solución se basa en las funcionalidades nativas de OpenSSH y Git, sin requerir software adicional.

TL;DR (Resumen Corto) Link to heading

  1. Genera Claves Separadas: Crea un par de claves SSH único para cada identidad (p. ej., trabajo, personal).
    1
2

    ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_trabajo -C "trabajo@email.com"
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_personal -C "personal@email.com"
  2. Configura SSH: Edita el archivo ~/.ssh/config para crear alias de host que se asocien a la clave correcta.
    1

    Host github.com-trabajo

  HostName github.com
  IdentityFile ~/.ssh/id_ed25519_personal
  IdentitiesOnly yes
  3. Usa los Alias en Git: Al clonar o actualizar remotos, reemplaza el nombre de host real con tu nuevo alias.
    1
2

    # En lugar de git@github.com:...
git clone git@github.com-trabajo:empresa/proyecto.git

Configura Usuarios de Git (Recomendado): Usa includeIf en tu ~/.gitconfig para establecer automáticamente el user.name y user.email correctos basándose en el directorio del proyecto (p. ej., ~/proyectos/trabajo/). Esto asegura la autoría correcta de los commits y permite el firmado GPG específico por identidad.

1. Principios y Justificación Link to heading

Gestionar identidades a través de claves SSH individuales es una práctica de seguridad fundamental. Las justificaciones clave son:

  • Segregación de Identidades: Permite una separación estricta entre perfiles de desarrollo (personal, trabajo, clientes), asegurando que cada contribución y acceso se asocie correctamente con la identidad adecuada para auditorías y atribución de código.
  • Seguridad y Principio de Privilegio Mínimo: Al usar diferentes claves para diferentes servicios, el impacto de una clave privada comprometida es limitado. Una clave que da acceso a un único repositorio es un riesgo mucho menor que una clave maestra que da acceso a toda la infraestructura.
  • Auditabilidad y Trazabilidad: Simplifica el seguimiento de qué identidad (y, por lo tanto, qué clave) se utilizó para realizar una acción específica en un sistema.
  • Flexibilidad Operativa: Agiliza el proceso de conceder y revocar acceso. Para revocar el acceso a un servicio, simplemente eliminas la clave pública correspondiente de ese servicio sin afectar el acceso a otros.

2. Prerrequisitos Link to heading

Antes de comenzar, asegúrate de tener instalado el siguiente software:

  • Git: Versión 2.13 o superior.
  • Cliente OpenSSH: Estándar en macOS, la mayoría de las distribuciones de Linux, y disponible en Windows (a través de PowerShell, Git Bash o WSL).

Nota: Se asume que trabajarás desde un directorio ~/.ssh estándar. Si existe una configuración previa, crea una copia de seguridad antes de proceder.

3. Paso 1: Generando Tus Claves SSH Link to heading

Se debe generar un par de claves único para cada identidad que necesites gestionar.

3.1. Eligiendo el Algoritmo Link to heading

Se recomienda encarecidamente el uso de Ed25519. Ofrece una seguridad comparable a RSA de 3072 bits con claves mucho más cortas, lo que resulta en un rendimiento superior. RSA es una alternativa aceptable para la compatibilidad con sistemas heredados.

3.2. Nomenclatura y Generación Estándar Link to heading

Para asegurar la consistencia, utiliza la siguiente convención de nomenclatura para tus archivos de clave y comentarios.

Acción Crítica de Seguridad: Cuando se te solicite, siempre asigna una frase de contraseña robusta a cada clave privada. Esto cifra la clave privada en tu disco, proporcionando una capa vital de protección.

  • Nombre del Archivo de Clave (-f): ~/.ssh/id_<algoritmo>_<contexto>_<servicio>
    • <algoritmo>: ed25519 o rsa.
    • <contexto>: trabajo, personal, cliente_nombrecliente.
    • <servicio>: github, gitlab, azure, servidor_prod, etc.
  • Comentario de la Clave (-C): "<email> - <dispositivo> - <AAAA-MM-DD>"
    • <email>: El correo electrónico asociado con la identidad.
    • <dispositivo>: Un identificador de la máquina (p. ej., MacBookProM3, WorkstationDell).
    • <AAAA-MM-DD>: La fecha de creación de la clave.

Ejemplos de Aplicación:

1
2
3
4
5

# Clave para una cuenta de trabajo de GitHub en un MacBook Pro
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_trabajo_github -C "nombre.apellido@empresa.com - MacBookProM3 - 2025-09-25"

# Clave para una cuenta personal de GitLab en la misma máquina
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_personal_gitlab -C "email.personal@example.com - MacBookProM3 - 2025-09-25"

4. Paso 2: Gestionando Claves con el Agente SSH Link to heading

El ssh-agent es un servicio en segundo plano que almacena de forma segura tus claves privadas descifradas en la memoria, para que no tengas que introducir la frase de contraseña cada vez que se utiliza una clave.

4.1. Iniciar el Agente SSH Este comando debe ejecutarse al comienzo de una nueva sesión de terminal.

1

eval "$(ssh-agent -s)"

Nota: Muchas terminales y sistemas operativos modernos gestionan esto automáticamente por sesión.

4.2. Cargar Claves en el Agente Añade las claves privadas que acabas de generar.

1
2

ssh-add ~/.ssh/id_ed25519_trabajo_github
ssh-add ~/.ssh/id_ed25519_personal_gitlab

4.3. Persistencia (macOS) En macOS, puedes integrar ssh-agent con el Llavero (Keychain) del sistema para almacenar las frases de contraseña de forma segura. La forma más eficiente es a través del archivo de configuración de SSH, pero también puedes añadirlas manualmente:

1

ssh-add --apple-use-keychain ~/.ssh/id_ed25519_trabajo_github

5. Paso 3: Configurando el Cliente SSH (~/.ssh/config) Link to heading

Esta es la parte central de la configuración, donde defines reglas para que tu cliente SSH seleccione la clave correcta para cada conexión.

5.1. Crear y Proteger el Archivo de Configuración Si el archivo no existe, créalo y establece los permisos adecuados para asegurar que solo tú puedas leerlo y escribirlo.

1
2

touch ~/.ssh/config
chmod 600 ~/.ssh/config

5.2. Definir Hosts y sus Identidades Edita el archivo ~/.ssh/config para añadir una entrada Host para cada identidad. Estas entradas son alias que mapean un nombre de host personalizado a una configuración de conexión específica.

#--- Cuenta de GitHub del Trabajo ---
Host github.com-trabajo
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_trabajo_github
  IdentitiesOnly yes
  AddKeysToAgent yes
  UseKeychain yes # Directiva específica de macOS para guardar la frase de contraseña en el Llavero

#--- Cuenta Personal de GitLab ---
Host gitlab.com-personal
  HostName gitlab.com
  User git
  IdentityFile ~/.ssh/id_ed25519_personal_gitlab
  IdentitiesOnly yes
  AddKeysToAgent yes
  UseKeychain yes # Específico de macOS

#--- Servidor de Producción del Cliente X ---
Host cliente-x-prod
  HostName 123.45.67.89
  User admin_user
  IdentityFile ~/.ssh/id_ed25519_cliente_x_servidor_prod
  IdentitiesOnly yes
  Port 2222 # Ejemplo de un puerto no estándar

#--- Configuración Global (Opcional) ---
# Se aplica a todos los hosts a menos que se anule
Host *
  ServerAliveInterval 60
  TCPKeepAlive yes

Justificación de las Directivas Clave:

  • Host: Define un alias único para la conexión (p. ej., github.com-trabajo).
  • HostName: El nombre de dominio real o la dirección IP del servidor.
  • User: El nombre de usuario para la conexión (casi siempre git para los proveedores de Git).
  • IdentityFile: La ruta a la clave privada que se utilizará.
  • IdentitiesOnly yes: Directiva crítica de seguridad. Obliga a SSH a usar únicamente la identidad especificada en IdentityFile, evitando que intente con otras claves y cause posibles bloqueos de cuenta.
  • AddKeysToAgent yes: Añade automáticamente la clave al ssh-agent en su primer uso.
  • UseKeychain yes: (macOS) Almacena la frase de contraseña de la clave en el Llavero de macOS después del primer uso.

6. Paso 4: Añadiendo Claves Públicas a Servicios Remotos Link to heading

La clave pública (.pub) debe ser registrada en el servicio de destino para verificar tu identidad.

6.1. Copiar la Clave Pública

  • macOS:
    1

    pbcopy < ~/.ssh/id_ed25519_trabajo_github.pub
  • Linux (requiere xclip):
    1

    xclip -selection clipboard < ~/.ssh/id_ed25519_trabajo_github.pub
  • Windows (Git Bash):
    1

    cat ~/.ssh/id_ed25519_trabajo_github.pub | clip

6.2. Registrar la Clave Pública

  • Para Proveedores de Git (GitHub, GitLab, etc.): Navega a la sección “SSH and GPG keys” en la configuración de tu cuenta y pega el contenido de la clave pública.
    • Buena Práctica: Dale a la clave un nombre descriptivo en la interfaz del proveedor, como MacBookPro M3 (Trabajo) o PC-Escritorio-Casa (Personal).
  • Para Servidores SSH:
    • Método Recomendado (ssh-copy-id): Esta utilidad gestiona el proceso de forma segura.
      1

      ssh-copy-id cliente-x-prod # Usa el alias de ~/.ssh/config
    • Método Manual (si ssh-copy-id no está disponible):
      1

      cat ~/.ssh/id_ed25519_cliente_x_servidor_prod.pub | ssh cliente-x-prod "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"

6.3. Verificar la Conexión Usa el alias Host para probar la autenticación.

1
2
3
4
5

ssh -T git@github.com-trabajo
# Respuesta esperada: Hi username! You've successfully authenticated...

ssh -T git@gitlab.com-personal
# Respuesta esperada: Welcome to GitLab, @username!

7. Paso 5: Configurando Git para Múltiples Identidades y Firmado GPG Link to heading

Para asegurar que los commits se atribuyan al autor correcto y estén firmados criptográficamente por la clave GPG correcta, utiliza la función de configuración condicional de Git. Este enfoque es el más robusto y escalable.

1. Configura tu estructura de directorios: Organiza tus proyectos en directorios específicos de cada contexto (p. ej., ~/proyectos/trabajo/ y ~/proyectos/personal/).

2. Edita tu ~/.gitconfig global: Añade directivas includeIf para cargar archivos de configuración adicionales según la ruta del repositorio.

[user]
    # Identidad por defecto (p. ej., personal)
    name = Tu Nombre Personal
    email = tu.email.personal@example.com

[core]
  excludesfile = ~/.gitignore_global

# --- Inclusiones Condicionales ---
[includeIf "gitdir:~/proyectos/trabajo/"]
    path = ~/proyectos/trabajo/.gitconfig

[includeIf "gitdir:~/proyectos/personal/"]
    path = ~/proyectos/personal/.gitconfig

3. Crea los archivos .gitconfig específicos del directorio: En estos archivos, puedes especificar no solo los detalles del usuario, sino también la clave GPG a utilizar para firmar commits dentro de ese contexto.

  • En ~/proyectos/trabajo/.gitconfig:
    1

    [user]
    name = Tu Nombre de Trabajo
    email = tu.email@empresa.com
    # Opcional: Clave GPG para firmar commits de trabajo
    signingkey = A1B2C3D4E5F6G7H8

# Opcional: Para firmar todos los commits en este contexto por defecto
[commit]
   gpgsign = true
  • En ~/proyectos/personal/.gitconfig:
    1
2
3
4
5

7

    [user]
    name = Tu Nombre Personal
    email = tu.email.personal@example.com
    signingkey = 1A2B3C4D5E6F7G8H

[commit]
   gpgsign = true

Con esta configuración, cualquier repositorio dentro de ~/proyectos/trabajo/ usará automáticamente tu identidad de trabajo y la clave GPG correspondiente para los commits.

8. Paso 6: Flujo de Trabajo con Repositorios Link to heading

8.1. Clonando un Nuevo Repositorio Link to heading

Al clonar, modifica la URL SSH para usar el alias Host definido en ~/.ssh/config.

  • URL Original: git@github.com:nombre-organizacion/proyecto.git
  • URL Modificada para identidad de trabajo: git@github.com-trabajo:nombre-organizacion/proyecto.git

Flujo de Trabajo de Ejemplo:

# Navega al directorio de trabajo
cd ~/proyectos/trabajo

# Clona usando el alias de trabajo
git clone git@github.com-trabajo:organizacion-trabajo/proyecto-cliente.git

# Git usará automáticamente la identidad y clave GPG de trabajo debido a la configuración includeIf
cd proyecto-cliente
git config --get user.email # Debería devolver tu.email@empresa.com

8.2. Actualizando un Repositorio Existente Link to heading

Si un repositorio fue clonado previamente con una URL diferente (HTTPS o la URL SSH por defecto), actualiza la URL del remote.

1
2

cd /ruta/al/proyecto
git remote set-url origin git@github.com-trabajo:organizacion-trabajo/proyecto-cliente.git

9. Paso 7: Certificando Commits (--signoff) Link to heading

Certificar un commit es diferente a firmarlo con GPG. Es una forma simple y no criptográfica de certificar que tienes el derecho de enviar el trabajo. Esto es comúnmente requerido por proyectos que utilizan un Certificado de Origen del Desarrollador (DCO).

La certificación añade un pie de página Signed-off-by: al final del mensaje del commit, que incluye tu nombre y correo electrónico de la configuración de Git.

Cómo Usarlo: Para añadir una certificación a un commit, usa el flag -s o --signoff.

1

git commit -s -m "Tu mensaje de commit"

Esto no reemplaza el firmado GPG (git commit -S), que proporciona una verificación criptográfica de la identidad. Ambos pueden ser usados juntos si un proyecto lo requiere.

10. Gestión de Riesgos y Consideraciones de Seguridad Link to heading

  • Permisos de Archivos: Es imperativo mantener los permisos correctos.
    • Directorio ~/.ssh: 700 (drwx——)
    • Claves privadas (id_*): 600 (-rw——-)
    • Claves públicas (id_*.pub): 644 (-rw-r–r–)
  • Rotación de Claves: Establece una política para rotar las claves SSH periódicamente (p. ej., anualmente), especialmente para entornos de producción.
  • Exposición de Clave Privada: Una clave privada nunca debe ser compartida, versionada en Git o almacenada en texto plano en ubicaciones inseguras.

11. Solución de Problemas Link to heading

  • Permission denied (publickey):
    1. Verifica la conexión con ssh -vT git@<alias-host>. El modo verboso (-v) te mostrará qué archivo de identidad está intentando usar.
    2. Confirma que la clave pública correcta está en el servidor/servicio.
    3. Asegúrate de que ssh-agent esté en ejecución y tenga la clave cargada (ssh-add -l).
    4. Verifica los permisos de los archivos y directorios en ~/.ssh.
  • WARNING: UNPROTECTED PRIVATE KEY FILE!:
    • Los permisos en tu archivo de clave privada son demasiado abiertos. Arréglalo con chmod 600 ~/.ssh/tu_clave_privada.
  • Git está usando la identidad incorrecta:
    • Dentro del repositorio, ejecuta git config --list --show-origin para ver de dónde se origina cada valor de configuración, ayudándote a depurar las directivas includeIf.
  • Broken pipe fatal: Could not read from remote repository: Esto puede ser un problema de conexión. Añadir ServerAliveInterval 60 y TCPKeepAlive yes a la entrada de tu host en ~/.ssh/config puede ayudar.
  • Problemas de Conexión con Azure: Si ves un mensaje como The authenticity of host 'ssh.dev.azure.com (X.X.X.X)' can't be established, es una advertencia estándar de la primera conexión. Puedes escribir yes para continuar. El mensaje remote: Shell access is not supported. es normal para los proveedores de Git.

Apéndice B: Seguridad Avanzada - Integración con Gestores de Secretos Link to heading

Para una seguridad mejorada, las claves SSH privadas pueden ser gestionadas por herramientas externas, eliminando la necesidad de almacenarlas directamente en el disco.

  • 1Password: El cliente de escritorio de 1Password puede actuar como un ssh-agent. Las claves SSH se almacenan de forma segura en la bóveda de 1Password y se cargan en el agente solo cuando es necesario, autenticando al usuario a través del gestor de contraseñas.
  • HashiCorp Vault: En infraestructuras más complejas, Vault puede generar credenciales SSH de corta duración (certificados SSH) bajo demanda. Esto elimina por completo las claves estáticas de larga duración, alineándose con un modelo de seguridad de confianza cero (zero-trust).

La implementación de estas soluciones está fuera del alcance de esta guía básica, pero debe considerarse como el siguiente paso evolutivo para fortalecer la seguridad del acceso de los desarrolladores.

#!/bin/bash

# Script para configurar la estructura de directorios y los archivos .gitconfig condicionales.

echo "--- Iniciando la configuración del entorno de desarrollo para múltiples identidades de Git ---"

# --- Definición de Variables ---
# Pide al usuario que introduzca sus datos.
read -p "Introduce tu nombre completo para el trabajo: " WORK_NAME
read -p "Introduce tu email de trabajo: " WORK_EMAIL
read -p "Introduce tu nombre completo personal: " PERSONAL_NAME
read -p "Introduce tu email personal: " PERSONAL_EMAIL

# Rutas a los directorios de proyectos
WORK_DIR="$HOME/proyectos/trabajo"
PERSONAL_DIR="$HOME/proyectos/personal"
GLOBAL_GITCONFIG="$HOME/.gitconfig"

# --- Creación de Directorios y Archivos de Configuración ---
echo "Creando directorios de proyectos y archivos .gitconfig..."
mkdir -p "$WORK_DIR"
cat > "$WORK_DIR/.gitconfig" << EOL
[user]
    name = $WORK_NAME
    email = $WORK_EMAIL
EOL

mkdir -p "$PERSONAL_DIR"
cat > "$PERSONAL_DIR/.gitconfig" << EOL
[user]
    name = $PERSONAL_NAME
    email = $PERSONAL_EMAIL
EOL
echo "Directorios y archivos .gitconfig específicos creados."

# --- Modificación del .gitconfig global ---
GLOBAL_GITCONFIG="$HOME/.gitconfig"
echo "Modificando el archivo .gitconfig global en $GLOBAL_GITCONFIG..."

# Hace una copia de seguridad del .gitconfig global si ya existe
if [ -f "$GLOBAL_GITCONFIG" ]; then
    cp "$GLOBAL_GITCONFIG" "$GLOBAL_GITCONFIG.bak_$(date +%F)"
    echo "Copia de seguridad del .gitconfig global creada en $GLOBAL_GITCONFIG.bak_..."
fi

# Añade las directivas includeIf al final del archivo global.
# Esto es idempotente; no las añadirá si ya existen.
if ! grep -q "gitdir:$WORK_DIR/" "$GLOBAL_GITCONFIG"; then
    cat >> "$GLOBAL_GITCONFIG" << EOL

# --- Inclusiones Condicionales para Múltiples Identidades ---
[includeIf "gitdir:$WORK_DIR/"]
    path = $WORK_DIR/.gitconfig
[includeIf "gitdir:$PERSONAL_DIR/"]
    path = $PERSONAL_DIR/.gitconfig
EOL
    echo "Directivas includeIf añadidas al .gitconfig global."
else
    echo "Las directivas includeIf ya existen en el .gitconfig global. No se realizaron cambios."
fi

echo "--- Configuración completada ---"
echo "Ahora, clona tus repositorios de trabajo en $WORK_DIR y los personales en $PERSONAL_DIR."
echo "Git usará automáticamente la identidad correcta para cada uno."
