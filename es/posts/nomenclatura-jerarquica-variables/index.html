Propuesta de Estándar: Nomenclatura Jerárquica para Variables de lo General a lo Específico Link to heading

**** Nota: Este artículo fue actualizado y su URL modificada el 2025-04-19. ****

El Problema: Nombres de Variables Inconsistentes y Caóticos Link to heading

Al programar, especialmente en el desarrollo de UI y sistemas de diseño, el nombramiento de variables es fundamental. Sin embargo, un enfoque ad-hoc y espontáneo a menudo conduce a convenciones incoherentes, especialmente a medida que el proyecto crece o participan más colaboradores. Recordar nombres exactos se vuelve una carga, lo que resulta en búsquedas globales ineficientes, refactorizaciones costosas y una disminución general de la legibilidad y mantenibilidad del código. Necesitamos un enfoque estructurado y predecible.

Síntomas Comunes del Problema:

  • primaryColor vs main_color vs themePrimary
  • buttonHover vs btnMouseOver vs hoverButtonBg
  • text_size_small vs smallFontSize vs fontSzS
  • Variables ambiguas como highlight, border, temp, data
  • Dificultad para encontrar todas las variables relacionadas con un componente (button, card).
  • Inconsistencia al añadir nuevas variantes (¿darkRed, redDark, darkerRed?).

La Solución: Nomenclatura Jerárquica Modular y Predictiva Link to heading

Proponemos un estándar de nomenclatura basado en una jerarquía clara y consistente, ordenando las partes del nombre de lo general a lo específico, de izquierda a derecha. Este enfoque no solo agrupa lógicamente las variables relacionadas, sino que mejora drásticamente la predictibilidad, la mantenibilidad y aprovecha al máximo las capacidades de autocompletado de los IDEs modernos.

El Patrón Central Recomendado:

La estructura general que recomendamos sigue este orden:

[Categoría/Contexto] -> Elemento/Componente -> Propiedad/Atributo -> [Variante/Estado]

Donde:

  • [Categoría/Contexto] (Opcional pero recomendado en sistemas grandes): Un agrupador de alto nivel que define un área funcional, tema o sub-sistema (ej: ui-kit, theme, feature-auth, semantic-color). A menudo puede estar implícito por la ubicación del archivo/módulo, pero explicitarlo en el nombre aumenta la claridad global.
  • Elemento/Componente: El sujeto principal al que se aplica la variable. Puede ser un componente UI específico (button, card, input), un concepto abstracto (color, spacing, font, border, icon), o incluso una entidad más amplia (userProfile, searchResults).
  • Propiedad/Atributo: La característica específica que se está definiendo para el Elemento (ej: color, size, font-family, background-color, margin, z-index, opacity, padding, weight).
  • [Variante/Estado] (Opcional): Modificadores que especifican una variación, estado o excepción a la norma. Esto incluye estados interactivos (hover, focus, disabled, active), variantes semánticas o de propósito (primary, secondary, error, success, info), tamaños (large, small, compact), estilos visuales (light, dark, subtle) u otras distinciones necesarias. Se pueden encadenar si es lógico y necesario (ej: disabled-light).

Nota sobre Casos “Default” o “Base”:

Para el valor más común o por defecto de una propiedad, se recomienda usar el nombre más corto y directo posible (ej: textColor, buttonBackgroundColor) si no genera ambigüedad en el contexto. Los sufijos como -default, -base, o -medium pueden usarse cuando sea necesario diferenciar explícitamente la variante principal de otras (ej: fontSizeMedium vs fontSizeLarge, colorBrandBase vs colorBrandDark). La consistencia dentro de un grupo de variables relacionadas es clave.

Nota sobre Convenciones de Casos:

Esta estructura jerárquica es el concepto fundamental. Debe adaptarse a las convenciones de mayúsculas/minúsculas estándar del lenguaje o plataforma específica:

  • CSS/SCSS/Less: kebab-case (ej: --button-background-color-primary-hover)
  • JavaScript/TypeScript: camelCase (ej: buttonBackgroundColorPrimaryHover) o PascalCase para constantes/enums si la guía de estilo lo indica.
  • Dart/Flutter: camelCase (ej: buttonBackgroundColorPrimaryHover)
  • JSON/YAML (Tokens): kebab-case o camelCase son comunes.
  • Swift: camelCase (ej: buttonBackgroundColorPrimaryHover)

  --button-primary-background-color-hover: cyan;
  --button-primary-text-color-default: black;
  --input-error-border-color: orange; /* Ejemplo: Error en Dark es naranja */
  /* ...etc */
}

Beneficios Clave de la Nomenclatura Jerárquica Link to heading

  1. Legibilidad y Comprensión: La estructura predecible hace que el código sea auto-explicativo. Es fácil deducir el propósito de una variable sin necesidad de buscar su definición.
  2. Mantenibilidad y Refactorización: Encontrar y modificar variables relacionadas es trivial. Cambiar un color base o un tamaño afecta a todas las variables que derivan de él de forma organizada.
  3. Autocompletado Potenciado (IntelliSense): Escribir la parte general (button-, text-color-, theme-dark-) permite al IDE filtrar y sugerir rápidamente las opciones específicas disponibles. Esto reduce drásticamente la carga cognitiva y los errores tipográficos.
  4. Colaboración Consistente: Un estándar claro y compartido elimina la ambigüedad y asegura que todos los miembros del equipo (incluyendo futuros miembros) nombren las variables de manera uniforme.
  5. Escalabilidad: El sistema se adapta bien a medida que el proyecto crece en complejidad, número de componentes o variantes de tema.
  6. Claridad Conceptual: Fomenta pensar en la estructura del sistema (componentes, propiedades, estados, variantes) de forma modular y sistemática durante el diseño y la codificación.

Relación con Principios de Diseño (SRP y Cohesión) Link to heading

Esta nomenclatura funciona de manera óptima cuando el código subyacente está bien estructurado. Si nombrar variables se vuelve excesivamente complejo o largo porque un único archivo, clase o componente intenta gestionar demasios conceptos dispares (colores base, estilos de botones específicos, configuración de API, lógica de negocio), puede ser una señal de alerta (code smell) indicando una baja cohesión o una violación del Principio de Responsabilidad Única (Single Responsibility Principle - SRP). Refactorizar hacia módulos, archivos o componentes más pequeños y cohesivos no solo mejora la organización general del código, sino que también simplifica enormemente la aplicación efectiva de este estándar de nomenclatura.

Alcance y Aplicabilidad Link to heading

Este patrón de nomenclatura jerárquica brilla especialmente en la definición de:

  • Design Tokens: Colores, tipografía, espaciado, sombras, radios, etc.
  • Variables de Estilo: CSS/SCSS/Less, CSS-in-JS, estilos en línea tipados (React Native, Flutter).
  • Variables de Configuración de UI: Temas (light/dark), densidades, modos de visualización.
  • Constantes de Interfaz: Claves de localización (ej: screenLoginButtonSubmitLabel), identificadores de eventos analíticos (ej: analyticsEventUserProfileEditSaveClick).

Aunque su origen está en la UI, el principio fundamental de nombrar jerárquicamente de lo general a lo específico es una heurística poderosa y valiosa aplicable a muchos otros dominios del nombramiento en programación (ej: configuración de backend, constantes de dominio, identificadores de recursos).

Conclusión Link to heading

Adoptar un estándar de nomenclatura jerárquico y modular como el propuesto ([Categoría] -> Elemento -> Propiedad -> [Variante/Estado]) requiere una disciplina inicial, pero los beneficios a largo plazo en legibilidad, mantenibilidad, colaboración y escalabilidad son inmensos. Proporciona una estructura robusta y predecible que reduce la fricción en el desarrollo y mejora la calidad general de la base de código. Es una inversión fundamental para la salud y longevidad de cualquier proyecto de software, especialmente aquellos con interfaces de usuario complejas o sistemas de diseño evolutivos.
