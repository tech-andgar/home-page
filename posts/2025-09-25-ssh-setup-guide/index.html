Ultimate Guide to Managing Multiple SSH Keys for Git and Server Access

Executive Summary Link to heading

This document establishes a comprehensive methodology for managing multiple SSH keys on a developer’s workstation. The primary goal is to ensure a clear and secure segregation of digital identities (e.g., personal vs. work) for interacting with Git repositories (GitHub, GitLab, etc.) and accessing remote servers. By adopting this guide, you will enhance security by applying the principle of least privilege, reduce the risk of commit attribution errors, and create a scalable solution for managing access to various resources. This solution relies on the native functionalities of OpenSSH and Git, requiring no additional software.

TL;DR Link to heading

  1. Generate Separate Keys: Create a unique SSH key pair for each identity (e.g., work, personal).
    1
2

    ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_work -C "work@email.com"
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_personal -C "personal@email.com"
  2. Configure SSH: Edit the ~/.ssh/config file to create host aliases that map to the correct key.
    1
2

4

6

    Host github.com-work
  HostName github.com
  IdentityFile ~/.ssh/id_ed25519_work
  IdentitiesOnly yes

Host github.com-personal
  HostName github.com
  IdentityFile ~/.ssh/id_ed25519_personal
  IdentitiesOnly yes
  3. Use Aliases in Git: When cloning or updating remotes, replace the real hostname with your new alias.
    1
2

    # Instead of git@github.com:...
git clone git@github.com-work:company/project.git
  4. Configure Git Users (Recommended): Use includeIf in your ~/.gitconfig to automatically set the correct user.name and user.email based on the project’s directory (e.g., ~/projects/work/). This ensures correct commit authorship and allows for identity-specific GPG signing.

1. Principles and Justification Link to heading

Managing identities through individual SSH keys is a fundamental security practice. The key justifications are:

  • Identity Segregation: It allows for a strict separation between development profiles (personal, work, clients), ensuring each contribution and access is correctly associated with the proper identity for auditing and code attribution.
  • Security and Principle of Least Privilege: By using different keys for different services, the impact of a compromised private key is limited. A key granting access to a single repository is a much smaller risk than a master key providing access to all infrastructure.
  • Auditability and Traceability: It simplifies tracking which identity (and therefore, which key) was used to perform a specific action on a system.
  • Operational Flexibility: It streamlines the process of granting and revoking access. To revoke access to a service, you simply remove the corresponding public key from that service without affecting access to others.

2. Prerequisites Link to heading

Before you begin, ensure you have the following software installed:

  • Git: Version 2.13 or higher.
  • OpenSSH Client: Standard on macOS, most Linux distributions, and available on Windows (via PowerShell, Git Bash, or WSL).

Note: It is assumed that you will work from a standard ~/.ssh directory. If a previous configuration exists, create a backup before proceeding.

3. Step 1: Generating Your SSH Keys Link to heading

A unique key pair must be generated for each identity you need to manage.

3.1. Choosing the Algorithm Link to heading

The use of Ed25519 is highly recommended. It offers security comparable to 3072-bit RSA with much shorter keys, resulting in superior performance. RSA is an acceptable alternative for compatibility with legacy systems.

3.2. Standard Naming and Generation Link to heading

To ensure consistency, use the following naming convention for your key files and comments.

Critical Security Action: When prompted, always assign a strong passphrase to each private key. This encrypts the private key on your disk, providing a vital layer of protection.

  • Key File Name (-f): ~/.ssh/id_<algorithm>_<context>_<service>
    • <algorithm>: ed25519 or rsa.
    • <context>: work, personal, client_clientname.
    • <service>: github, gitlab, azure, prod_server, etc.
  • Key Comment (-C): "<email> - <device> - <YYYY-MM-DD>"
    • <email>: The email associated with the identity.
    • <device>: A machine identifier (e.g., MacBookProM3, WorkstationDell).
    • <YYYY-MM-DD>: The key creation date.

Application Examples:

1
2
3
4
5

# Key for a work GitHub account on a MacBook Pro
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_work_github -C "firstname.lastname@company.com - MacBookProM3 - 2025-09-25"

# Key for a personal GitLab account on the same machine
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_personal_gitlab -C "personal.email@example.com - MacBookProM3 - 2025-09-25"

4. Step 2: Managing Keys with the SSH Agent Link to heading

The ssh-agent is a background service that securely stores your decrypted private keys in memory, so you don’t have to enter the passphrase every time a key is used.

4.1. Start the SSH Agent This command should be executed at the beginning of a new terminal session.

1

eval "$(ssh-agent -s)"

Note: Many modern terminals and operating systems manage this automatically per session.

4.2. Load Keys into the Agent Add the private keys you have just generated.

1
2

ssh-add ~/.ssh/id_ed25519_work_github
ssh-add ~/.ssh/id_ed25519_personal_gitlab

4.3. Persistence (macOS) On macOS, you can integrate ssh-agent with the system’s Keychain to store passphrases securely. The most efficient way is through the SSH config file, but you can also add them manually:

1

ssh-add --apple-use-keychain ~/.ssh/id_ed25519_work_github

5. Step 3: Configuring the SSH Client (~/.ssh/config) Link to heading

This is the central part of the setup, where you define rules for your SSH client to select the correct key for each connection.

5.1. Create and Secure the Configuration File If the file does not exist, create it and set the appropriate permissions to ensure only you can read and write to it.

1
2

touch ~/.ssh/config
chmod 600 ~/.ssh/config

5.2. Define Hosts and their Identities Edit the ~/.ssh/config file to add a Host entry for each identity. These entries are aliases that map a custom hostname to a specific connection configuration.

#--- Work GitHub Account ---
Host github.com-work
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_work_github
  IdentitiesOnly yes
  AddKeysToAgent yes
  UseKeychain yes # macOS-specific directive to save the passphrase in the Keychain

#--- Personal GitLab Account ---
Host gitlab.com-personal
  HostName gitlab.com
  User git
  IdentityFile ~/.ssh/id_ed25519_personal_gitlab
  IdentitiesOnly yes
  AddKeysToAgent yes
  UseKeychain yes # macOS-specific

#--- Client X Production Server ---
Host client-x-prod
  HostName 123.45.67.89
  User admin_user
  IdentityFile ~/.ssh/id_ed25519_client_x_prod_server
  IdentitiesOnly yes
  Port 2222 # Example of a non-standard port

#--- Global Settings (Optional) ---
# Applies to all hosts unless overridden
Host *
  ServerAliveInterval 60
  TCPKeepAlive yes

Justification of Key Directives:

  • Host: Defines a unique alias for the connection (e.g., github.com-work).
  • HostName: The actual domain name or IP address of the server.
  • User: The username for the connection (almost always git for Git providers).
  • IdentityFile: The path to the private key to be used.
  • IdentitiesOnly yes: Critical security directive. Forces SSH to only use the identity specified in IdentityFile, preventing it from trying other keys and causing potential account lockouts.
  • AddKeysToAgent yes: Automatically adds the key to ssh-agent on first use.
  • UseKeychain yes: (macOS) Stores the key’s passphrase in the macOS Keychain after the first use.

6. Step 4: Adding Public Keys to Remote Services Link to heading

The public key (.pub) must be registered with the target service to verify your identity.

6.1. Copy the Public Key

  • macOS:
    1

    pbcopy < ~/.ssh/id_ed25519_work_github.pub
  • Linux (requires xclip):
    1

    xclip -selection clipboard < ~/.ssh/id_ed25519_work_github.pub
  • Windows (Git Bash):
    1

    cat ~/.ssh/id_ed25519_work_github.pub | clip

6.2. Register the Public Key

  • For Git Providers (GitHub, GitLab, etc.): Navigate to the “SSH and GPG keys” section in your account settings and paste the public key content.
    • Good Practice: Give the key a descriptive name in the provider’s interface, such as MacBookPro M3 (Work) or Home-Desktop-PC (Personal).
  • For SSH Servers:
    • Recommended Method (ssh-copy-id): This utility handles the process securely.
      1

      ssh-copy-id client-x-prod # Use the alias from ~/.ssh/config
    • Manual Method (if ssh-copy-id is not available):
      1

      cat ~/.ssh/id_ed25519_client_x_prod_server.pub | ssh client-x-prod "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"

6.3. Verify the Connection Use the Host alias to test authentication.

1
2
3
4
5

ssh -T git@github.com-work
# Expected response: Hi username! You've successfully authenticated...

ssh -T git@gitlab.com-personal
# Expected response: Welcome to GitLab, @username!

7. Step 5: Configuring Git for Multiple Identities and GPG Signing Link to heading

To ensure commits are attributed to the correct author and are cryptographically signed by the correct GPG key, use Git’s conditional configuration feature. This approach is the most robust and scalable.

1. Set up your directory structure: Organize your projects into context-specific directories (e.g., ~/projects/work/ and ~/projects/personal/).

2. Edit your global ~/.gitconfig: Add includeIf directives to load additional configuration files based on the repository’s path.

[user]
    # Default identity (e.g., personal)
    name = Your Personal Name
    email = your.personal.email@example.com

[core]
  excludesfile = ~/.gitignore_global

# --- Conditional Includes ---
[includeIf "gitdir:~/projects/work/"]
    path = ~/projects/work/.gitconfig

[includeIf "gitdir:~/projects/personal/"]
    path = ~/projects/personal/.gitconfig

3. Create the directory-specific .gitconfig files: In these files, you can specify not only the user details but also the GPG key to use for signing commits within that context.

  • In ~/projects/work/.gitconfig:
    1

    [user]
    name = Your Work Name
    email = your.email@company.com
    # Optional: GPG key for signing work commits
    signingkey = A1B2C3D4E5F6G7H8

# Optional: To sign all commits in this context by default
[commit]
   gpgsign = true
  • In ~/projects/personal/.gitconfig:
    1

    [user]
    name = Your Personal Name
    email = your.personal.email@example.com
    signingkey = 1A2B3C4D5E6F7G8H

[commit]
   gpgsign = true

With this setup, any repository inside ~/projects/work/ will automatically use your work identity and corresponding GPG key for commits.

8. Step 6: Workflow with Repositories Link to heading

8.1. Cloning a New Repository Link to heading

When cloning, modify the SSH URL to use the Host alias defined in ~/.ssh/config.

  • Original URL: git@github.com:organization-name/project.git
  • Modified URL for work identity: git@github.com-work:organization-name/project.git

Example Workflow:

1

4

# Navigate to the work directory
cd ~/projects/work

# Clone using the work alias
git clone git@github.com-work:work-organization/client-project.git

# Git will automatically use the work identity and GPG key due to the includeIf config
cd client-project
git config --get user.email # Should return your.email@company.com

8.2. Updating an Existing Repository Link to heading

If a repository was previously cloned with a different URL (HTTPS or the default SSH URL), update the remote’s URL.

1
2

cd /path/to/project
git remote set-url origin git@github.com-work:work-organization/client-project.git

9. Step 7: Signing Off on Commits (--signoff) Link to heading

Signing off on a commit is different from GPG signing. It is a simple, non-cryptographic way to certify that you have the right to submit the work. This is commonly required by projects that use a Developer Certificate of Origin (DCO).

The sign-off adds a Signed-off-by: trailer at the end of the commit message, which includes your name and email from the Git configuration.

How to Use: To add a sign-off to a commit, use the -s or --signoff flag.

1

git commit -s -m "Your commit message"

This is not a replacement for GPG signing (git commit -S), which provides cryptographic verification of identity. Both can be used together if required by a project.

10. Risk Management and Security Considerations Link to heading

  • File Permissions: It is imperative to maintain correct permissions.
    • ~/.ssh directory: 700 (drwx——)
    • Private keys (id_*): 600 (-rw——-)
    • Public keys (id_*.pub): 644 (-rw-r–r–)
  • Key Rotation: Establish a policy for rotating SSH keys periodically (e.g., annually), especially for production environments.
  • Private Key Exposure: A private key should never be shared, versioned in Git, or stored in plaintext in insecure locations.

11. Troubleshooting Link to heading

  • Permission denied (publickey):
    1. Verify the connection with ssh -vT git@<host-alias>. The verbose mode (-v) will show you which identity file it is trying to use.
    2. Confirm that the correct public key is on the server/service.
    3. Ensure that ssh-agent is running and has the key loaded (ssh-add -l).
    4. Check the permissions of the files and directories in ~/.ssh.
  • WARNING: UNPROTECTED PRIVATE KEY FILE!:
    • The permissions on your private key file are too open. Fix this with chmod 600 ~/.ssh/your_private_key.
  • Git is using the wrong identity:
    • Inside the repository, run git config --list --show-origin to see where each configuration value originates, helping you debug includeIf directives.
  • Broken pipe fatal: Could not read from remote repository: This can be a connection issue. Adding ServerAliveInterval 60 and TCPKeepAlive yes to your ~/.ssh/config host entry can help.
  • Azure Connection Issues: If you see a message like The authenticity of host 'ssh.dev.azure.com (X.X.X.X)' can't be established, it’s a standard first-time connection warning. You can type yes to continue. The remote: Shell access is not supported. message is normal for Git providers.

Appendix A: Authentication Flowchart Link to heading

This diagram illustrates the process when a command like git push is executed.

sequenceDiagram participant Dev as Developer participant Git as Git Client participant SSH as SSH Client participant SSH_Config as ~/.ssh/config participant SSH_Agent as SSH Agent participant Remote as Remote Server (e.g., GitHub) Dev->>Git: git push origin main Git->>SSH: Invokes SSH with remote URL (e.g., git@github.com-work:org/repo.git) SSH->>SSH_Config: Parses configuration file SSH_Config-->>SSH: Finds "Host github.com-work" block and applies rules SSH->>SSH_Agent: Requests the decrypted private key alt Key is already loaded SSH_Agent-->>SSH: Returns key from memory else Key is not loaded SSH_Agent->>Dev: Asks for key's passphrase Dev->>SSH_Agent: Enters passphrase SSH_Agent-->>SSH: Returns decrypted key end SSH->>Remote: Initiates connection to real HostName (github.com) with the correct key Remote->>Remote: Validates the public key Remote-->>SSH: Authentication successful SSH-->>Git: Connection established Git->>Remote: Transfers push data

Appendix B: Advanced Security - Integration with Secrets Managers Link to heading

For enhanced security, private SSH keys can be managed by external tools, eliminating the need to store them directly on disk.

  • 1Password: The 1Password desktop client can act as an ssh-agent. SSH keys are stored securely in the 1Password vault and are loaded into the agent only when needed, authenticating the user through the password manager.
  • HashiCorp Vault: In more complex infrastructures, Vault can generate short-lived SSH credentials (SSH certificates) on demand. This completely eliminates static, long-lived keys, aligning with a zero-trust security model.

The implementation of these solutions is beyond the scope of this basic guide but should be considered as the next evolutionary step to strengthen developer access security.

#!/bin/bash

# Script to set up directory structure and conditional .gitconfig files.

echo "--- Starting development environment setup for multiple Git identities ---"

# --- Variable Definitions ---
# Asks the user to enter their details.
read -p "Enter your full name for work: " WORK_NAME
read -p "Enter your work email: " WORK_EMAIL
read -p "Enter your full personal name: " PERSONAL_NAME
read -p "Enter your personal email: " PERSONAL_EMAIL

# Paths to project directories
WORK_DIR="$HOME/projects/work"
PERSONAL_DIR="$HOME/projects/personal"
GLOBAL_GITCONFIG="$HOME/.gitconfig"

# --- Directory and Config File Creation ---
echo "Creating project directories and .gitconfig files..."
mkdir -p "$WORK_DIR"
cat > "$WORK_DIR/.gitconfig" << EOL
[user]
    name = $WORK_NAME
    email = $WORK_EMAIL
EOL

mkdir -p "$PERSONAL_DIR"
cat > "$PERSONAL_DIR/.gitconfig" << EOL
[user]
    name = $PERSONAL_NAME
    email = $PERSONAL_EMAIL
EOL
echo "Directories and specific .gitconfig files created."

# --- Modification of the global .gitconfig ---
GLOBAL_GITCONFIG="$HOME/.gitconfig"
echo "Modifying the global .gitconfig file at $GLOBAL_GITCONFIG..."

# Backs up the global .gitconfig if it already exists
if [ -f "$GLOBAL_GITCONFIG" ]; then
    cp "$GLOBAL_GITCONFIG" "$GLOBAL_GITCONFIG.bak_$(date +%F)"
    echo "Backup of global .gitconfig created at $GLOBAL_GITCONFIG.bak_..."
fi

# Appends the includeIf directives to the end of the global file.
# This is idempotent; it will not add them if they already exist.
if ! grep -q "gitdir:$WORK_DIR/" "$GLOBAL_GITCONFIG"; then
    cat >> "$GLOBAL_GITCONFIG" << EOL

# --- Conditional Includes for Multiple Identities ---
[includeIf "gitdir:$WORK_DIR/"]
    path = $WORK_DIR/.gitconfig
[includeIf "gitdir:$PERSONAL_DIR/"]
    path = $PERSONAL_DIR/.gitconfig
EOL
    echo "includeIf directives added to the global .gitconfig."
else
    echo "The includeIf directives already exist in the global .gitconfig. No changes were made."
fi

echo "--- Setup complete ---"
echo "Now, clone your work repositories into $WORK_DIR and your personal ones into $PERSONAL_DIR."
echo "Git will automatically use the correct identity for each."
