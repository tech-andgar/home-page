Intent-Driven Development vs Spec-Driven Development: Compass and Map

July 25, 2026 7-minute read
AI • Software Engineering • Methodology
AI • IDD • SDD • Software Engineering • Vibecoding • DevSecOps • Methodology • Intent • Specifications

Note: You can read the Spanish (Español) version of this article here.

Imagine you’re building a house. The blueprint tells contractors exactly what to build — room dimensions, door positions, electrical outlets. That’s SDD: precise, enforceable, no ambiguity.

But the blueprint doesn’t explain why you wanted a home office instead of a third bedroom, or why you chose an open kitchen. Six months later, when a contractor asks “can we move this wall?”, nobody can answer without that original reasoning.

IDD is the document that captures why you made those decisions. SDD is the blueprint. You need both.

Two emerging methodologies — Spec-Driven Development (SDD) and Intent-Driven Development (IDD) — answer different questions. SDD asks: what exactly do we build and how do we verify it? IDD asks: why does this system exist and what problem must it solve? They’re not competing. They’re complementary layers.

What is Intent-Driven Development? Link to heading

IDD treats intent — the why and what of a system — as the most important artifact you write.1

Think of it like a doctor writing a patient’s history before prescribing treatment. The prescription (code) changes. The diagnosis (intent) is durable.

The order of work flows downward:

1

Intent (why & what) → Spec (how to build) → Code (implementation)

Humans write and maintain intent. AI produces the code. The key insight: prompts are throwaway. Intent must outlive them.

Three Schools of IDD Link to heading

There are three ways teams practice IDD — think of them as increasing levels of structure:

SchoolWhat it looks likeGood forWatch out for
Build-FirstOne intent doc per project, kept shortSmall teams, fast-moving projectsDoesn’t scale across multiple features
Implementation-LastIntent added after the code existsTeams with existing TDD/DDD habitsIntent can feel like an afterthought
Tree-StructuredA folder of intent files organized by domainLarge projects, multiple teams, AI agentsNeeds initial setup investment

The Tree-Structured approach is the most useful for AI-era projects. Instead of one big document, it’s a folder called intent/ with files organized around three questions: Purpose (why does this exist?), User Context (who uses it and why?), and Means (what are the key architectural decisions and trade-offs?).

What is Spec-Driven Development? Link to heading

SDD separates what the system must do (the contract) from how the AI implements it (the code).2

A concrete example: instead of telling an AI “build me a login endpoint,” you write a spec that says:

  • Input: email + password
  • Success: returns JWT, logs the event
  • Failure modes: invalid credentials return 401, not 500; rate-limit after 5 attempts

That spec becomes a contract the AI must fulfill. Not a suggestion — a gate.

Three maturity levels (pick the one that fits your team):

  1. Spec-First — write the spec before you write any code
  2. Spec-Anchored — specs exist and stay in sync as code evolves
  3. Spec-as-Source — the spec literally generates the code (advanced)

SDD’s superpower: shell hooks. These are small bash scripts that run on every commit. They check “does this code match its spec?” in milliseconds, at zero AI token cost. The AI cannot argue with a bash script or charm its way past it.

Three Key IDD Proposals Link to heading

1. From Harness to Compass Link to heading

SDD uses a harness — constraints that stop the AI from doing the wrong thing. IDD uses a compass — direction that points the AI toward the right destination.

Analogy: A harness on a horse prevents it from running off a cliff. A compass tells a navigator which direction to sail. You need both: the compass to not sail toward the wrong continent, the harness to not fall off the edge.

My take: don’t choose. Use intent for direction, hooks for enforcement. They solve different failure modes.

2. Git-AI-Flow Link to heading

AI agents generate code much faster than humans can review it. That creates a pile-up.

Git-AI-Flow solves this with two branches:

  • ai-develop — where AI works continuously, 24/7
  • main — where humans promote stable, reviewed states on their own schedule

Analogy: Think of it like a factory floor vs. a shipping dock. The factory (AI) runs constantly. The dock (main) ships when humans say it’s ready. Nobody expects the shipping dock to keep up with the factory’s output in real time.

This matters because METR’s research found AI assistance gives developers a perceived +24% speed boost but a real -19% slowdown on complex tasks — because human review becomes the bottleneck. Git-AI-Flow explicitly designs around that.

3. Intent Storming Link to heading

Before writing any code, gather the team (or just you and an AI) for a structured conversation: why are we building this? What decisions have we already made? What are we explicitly NOT building?

The output isn’t meeting notes. It’s an intent tree — a set of files capturing the reasoning behind the system before implementation starts.

Analogy: Event Storming maps what happens in a business domain (events, commands, aggregates). Intent Storming maps why decisions were made before the domain even has events. It’s the session that happens the week before the Event Storming workshop.

How They Complement Each Other Link to heading

IDD’s own documentation is explicit: “Compatible with Spec-Driven Development as a downstream layer.”1

The full stack looks like:

    ↓

    ↓

IDD without SDD = you know where you’re going but nothing stops the AI from taking a wrong turn on the way. Great vision, poor execution guardrails.

SDD without IDD = strict gates, but no memory. Six months later, a new engineer asks “why does this spec say no guest checkout?” and nobody knows. The reasoning was never written down.

Both together = the full chain: intent explains the why, specs define the what, hooks enforce the how. A new team member (or AI agent) can trace any decision from business goal to deployed line of code.

When to Use Which Link to heading

SituationRecommendation
Greenfield project with AI agentsIDD first (intent tree), then SDD (specs + hooks)
Existing codebase adding AI assistanceSDD first (gates protect what exists), IDD later for new features
Solo developer, small projectSDD minimum (constitution + hooks) is sufficient
Enterprise with multiple teamsBoth — IDD for cross-team alignment, SDD for per-team enforcement
“Haunted codebase” recoverySDD immediately (stop the bleeding), then IDD to rebuild shared understanding

The Practitioner’s Take Link to heading

I’ve been implementing the 5-step hardening manual (SDD + DevSecOps gates) in production. It works. The hooks catch real bugs. The specs prevent architectural drift. But I’ve noticed the gap IDD identifies: when I ask why a spec exists, the answer lives in my head or a Slack thread — not in a durable artifact.

IDD fills that gap. Not as a replacement, but as the upstream layer that makes specs meaningful rather than merely enforced.

Start with whichever solves your current pain:

  • Bugs escaping to production? → SDD (gates)
  • Team can’t explain architectural decisions? → IDD (intent tree)
  • Both? → Both. They stack cleanly.
