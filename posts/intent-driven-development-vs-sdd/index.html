Intent-Driven Development vs Spec-Driven Development: Compass and Map

July 25, 2026 5-minute read
AI • Software Engineering • Methodology
AI • IDD • SDD • Software Engineering • Vibecoding • DevSecOps • Methodology • Intent • Specifications

Intent-Driven Development vs Spec-Driven Development: Compass and Map Link to heading

The AI coding era exposed a gap that neither TDD nor BDD were designed to fill: who owns the “why” when the machine writes the “how”?

Two emerging methodologies answer this from different altitudes. Spec-Driven Development (SDD) treats specs as enforceable contracts — the map. Intent-Driven Development (IDD) treats intent as the durable source of truth above specs — the compass. They’re not competing. They’re complementary layers.

What is Intent-Driven Development? Link to heading

IDD is a discipline that treats intent — the durable description of why a system exists and what it must achieve — as the primary artifact of software work.1

The hierarchy flows downward:

1

Intent (why & what) → Spec (how to build) → Code (implementation)

Humans curate intent. Agents, AI, or humans produce implementation. The key insight: prompts are ephemeral. Intent must be durable.

Three Schools of IDD Link to heading

SchoolApproachStrengthLimitation
Build-FirstLightweight, Agile-alignedAvoids documentation decaySingle document per project; no reuse
Implementation-LastExtends DDD/TDD patternsStable quality verificationIntent as monolithic bundle
Tree-StructuredHierarchical intent across domainsCross-domain reuse; integrated workflowsRequires upfront structural investment

The Tree-Structured school is the most complete for AI-era projects: it organizes intent into a navigable folder of markdown files answering Purpose (why), User Context (who), and Means (how — at the strategic level, not implementation detail).

What is Spec-Driven Development? Link to heading

SDD separates the what (business contracts) from the how (syntax), using specs as non-negotiable contracts that AI must implement against.2

Three maturity levels:

  1. Spec-First — documentation exists before code
  2. Spec-Anchored — specs stay synchronized with implementation
  3. Spec-as-Source — specs generate code (the spec is the source)

SDD’s enforcement mechanism: deterministic shell hooks (“muscles”) that run in milliseconds at zero token cost. The AI cannot skip them.

Three Key IDD Proposals Link to heading

1. From Harness to Compass Link to heading

A framing shift: “A harness restrains; a compass gives direction.” Rather than treating AI as an entity requiring constraint (SDD’s shell hooks), IDD frames governance as providing strategic direction. The AI is trusted within the boundaries of curated intent.

My take: both are needed. The compass prevents wrong direction. The harness prevents wrong execution. Use intent for direction, hooks for enforcement.

2. Git-AI-Flow Link to heading

A dual-branch model: AI agents work continuously on ai-develop while humans selectively promote stable states to main on their own timeline. This decouples AI velocity from human review cadence.

This solves a real problem — the METR data shows human review is the bottleneck (+24% perceived speed, -19% actual speed). Git-AI-Flow explicitly buffers that gap.

3. Intent Storming Link to heading

Structured pre-coding workshops (team or solo with AI) to articulate technology decisions and intent as deliverables before implementation. Creates intent trees documenting rationale, replacing scattered meeting notes.

Think of it as Event Storming’s upstream cousin — instead of mapping domain events, you map why decisions were made.

How They Complement Each Other Link to heading

IDD’s own documentation is explicit: “Compatible with Spec-Driven Development as a downstream layer.”1

The full stack looks like:

Stakeholder objectives
    ↓
IDD (intent layer — natural language, durable)
    ↓
SDD (spec layer — contracts, enforceable)

IDD without SDD = clear direction, no enforcement. The AI knows why but nothing stops it from violating contracts.

SDD without IDD = strict gates, no compass. The specs enforce what, but the team can’t explain why decisions were made 6 months later.

Both together = intent drives specs, specs drive gates, gates drive code. Full traceability from business purpose to deployed artifact.

When to Use Which Link to heading

SituationRecommendation
Greenfield project with AI agentsIDD first (intent tree), then SDD (specs + hooks)
Existing codebase adding AI assistanceSDD first (gates protect what exists), IDD later for new features
Solo developer, small projectSDD minimum (constitution + hooks) is sufficient
Enterprise with multiple teamsBoth — IDD for cross-team alignment, SDD for per-team enforcement
“Haunted codebase” recoverySDD immediately (stop the bleeding), then IDD to rebuild shared understanding

The Practitioner’s Take Link to heading

I’ve been implementing the 5-step hardening manual (SDD + DevSecOps gates) in production. It works. The hooks catch real bugs. The specs prevent architectural drift. But I’ve noticed the gap IDD identifies: when I ask why a spec exists, the answer lives in my head or a Slack thread — not in a durable artifact.

IDD fills that gap. Not as a replacement, but as the upstream layer that makes specs meaningful rather than merely enforced.

Start with whichever solves your current pain:

  • Bugs escaping to production? → SDD (gates)
  • Team can’t explain architectural decisions? → IDD (intent tree)
  • Both? → Both. They stack cleanly.
