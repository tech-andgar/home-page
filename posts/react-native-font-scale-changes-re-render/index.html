React Native on Android: Live Font-Scale Changes Don't Re-render What You Think

July 8, 2026 4-minute read
Engineering
React-Native • Android • Accessibility • Debugging • Expo

The symptom Link to heading

A QA tester bumped the system font size in Android’s Display size & text settings while our app was open, went back to the app, and found button labels and status chips truncated — "Deposit" became "Dep..", "Completed" became "Complet". A previous fix for a related “app not loading” defect had already shipped, so this looked like a regression.

First theory: it’s a memo bug (partially true) Link to heading

React Native provides a scale multiplier via useWindowDimensions().fontScale. Our button component used it to compute a manually-scaled label style:

1
2
3
4

const combinedLabelStyle = useMemo(() => {
    return { ...getLabelStyle(theme, size, fontScale), ...labelStyle };
    // eslint-disable-next-line react-hooks/exhaustive-deps
}, [theme, size, labelStyle]); // <-- fontScale used inside, but missing from deps

The eslint-disable was hiding a real bug: when the OS font scale changed while the app stayed in the foreground, this memo never recomputed. The button kept using its original font size while the underlying Text (which auto-scales unless allowFontScaling={false}) rendered larger — mismatch, container too narrow, ellipsis kicks in.

Fixing the dependency array made buttons scale correctly. But a different component (a status chip) exhibited the same symptom, and it didn’t even reference fontScale in its styles.

Second theory: nothing re-renders at all (also true) Link to heading

Testing live, in an emulator, with adb shell settings put system font_scale X while the app sat in the foreground: nothing updated — not the button, not the chip, not even plain <Text> showing a dollar amount. Even the native screen header title truncated. That ruled out a single-component bug; something more fundamental wasn’t propagating the change to JS at all.

Digging into react-native’s Android source (DeviceInfoModule.kt) explained why:

1
2
3
4
5
6
7

override fun onHostResume() {
    val newFontScale = reactApplicationContext.resources?.configuration?.fontScale
    if (newFontScale != null && newFontScale != fontScale) {
        fontScale = newFontScale
        emitUpdateDimensionsEvent()
    }
}

Dimensions/useWindowDimensions() on Android is only updated on the Activity’s resume lifecycle callback — not on onConfigurationChanged. If you change the font scale without backgrounding the app, React Native has no idea anything changed until the next resume.

This matters because a related earlier fix had deliberately added fontScale|density to android:configChanges in MainActivity, specifically so a font-scale change would not destroy and recreate the Activity (that was causing a “splash screen never hides” bug). The side effect: Android no longer tears down the view hierarchy on font-scale change, and RN’s own dimension-change detection only runs on resume — so nothing refreshes unless the user actually backgrounds and re-foregrounds the app.

The real fix, in two parts Link to heading

  1. Subscribe. Any component whose layout depends on fontScale must call useWindowDimensions() itself, not rely on a parent to pass it down as a prop that happens to update. Without the subscription, the component has no reason to re-render on resume.

  2. Force remeasurement, not just re-render. Even after subscribing, a style-only prop change wasn’t enough — Android’s underlying TextView measurement is cached and doesn’t relayout just because a StyleSheet object reference changed. The reliable fix was to key the component on the scale value itself:

    1

    <Pressable key={`fontscale-${fontScale.toFixed(2)}`} ...>

    This forces a full unmount/remount, which is exactly equivalent to a cold app launch at that font scale — which we’d already confirmed renders correctly.

How to actually test this Link to heading

The easy way to get a false negative: changing font scale via ADB while the app is in the foreground. That skips the only code path (onHostResume) that detects the change at all.

1
2
3

adb shell input keyevent KEYCODE_HOME        # background the app — required
adb shell settings put system font_scale 1.5 # change while backgrounded
adb shell am start -n <package>/.MainActivity # bring back to foreground (real resume)

Anything less than a real background → change → foreground cycle isn’t testing the bug users actually hit.

Takeaways Link to heading

  • android:configChanges trade-offs cut both ways: preventing Activity recreation fixes one class of bug (blank/frozen splash) but silently reintroduces staleness everywhere that assumed a fresh mount on every relevant configuration change.
  • eslint-disable-next-line react-hooks/exhaustive-deps is worth treating as a standing question, not a settled answer — it hid a dependency that mattered.
  • “It re-renders” and “it relayouts correctly” are different guarantees on native platforms. A key remount is a legitimate, sometimes necessary escape hatch when style updates alone don’t force native views to remeasure.
